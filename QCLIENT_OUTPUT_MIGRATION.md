# qclient output changes for Quilscan Agent

Source baseline: official `QuilibriumNetwork/monorepo` branch `v2.1.0.25` at `f2496cbf851569bf8d0f8d31a12526a14017f7e6` (pinned 2026-10-29, subpatch still `.111`). The Rust qclient implementation and its Cargo dependency closure follow that source, retaining the existing Quilscan commands below with their default availability, parameters, schemas and timeout policy. New local extension features are deferred. A matching version string alone does not identify this source revision.

Version display follows official `quil-config::display_version()` (currently `2.1.0.25.111`). Both `qclient --version` and the retained `qclient version` alias print `qclient 2.1.0.25.111`; `version --checksum` additionally prints checksums. These commands describe the source build. Quilscan Agent's update/reporting authority remains `qclient-version.json` plus installation state, including user-selected release suffixes such as `.88` or `.99`.

## `node prover manage --once`

The old space-delimited `Allocations (...)` and `Available Shards (...)` tables are replaced by one JSON document on stdout. Errors go to stderr and return a nonzero exit code. The command requests the official `GetNodeInfo`, `GetWorkerInfo`, and `GetShardInfo(include_all=true)` data and builds the same `Model` used by the interactive Manage screen. A failed node or shard request fails the command; it does not emit a partial snapshot. One-shot deadlines are 75 seconds for node info, 15 seconds for optional worker info, and 90 seconds for shard info. Node and worker reads run sequentially while the shard read runs concurrently, bounding reads to 90 seconds; with the 20-second connection timeout this fits the Agent's existing 120-second command deadline. Timeout errors identify the RPC/deadlines and do not retry. Interactive Manage retains its 15-second node/worker and 60-second shard deadlines; mutating-command deadlines are unchanged.

Top-level fields in schema version 1:

| Field | Type | Meaning |
| --- | --- | --- |
| `schema_version` | integer | Always `1` for this schema. |
| `peer_id` | string | Node peer ID. |
| `frame_number`, `last_received_frame`, `last_global_head` | integer | Official shard/node frame observations. |
| `current_epoch`, `epoch_length_frames` | integer | Official epoch context. |
| `running_workers`, `allocated_workers` | integer | Official node counts. |
| `worker_capacity` | integer or null | Configured capacity; zero/unreported Node capacity is null. |
| `draining_workers` | integer or null | Distinct workers marked draining; null when Worker RPC observations are unavailable. |
| `worker_info_available` | boolean | Whether Worker RPC returned observations during this snapshot. |
| `reachable` | boolean | Official node reachability result. |
| `allocations` | array | Official Manage allocation rows, including idle workers. |
| `available_shards` | array | Official Manage available shard rows. |

Each `allocations` row has `filter`, `worker`, `worker_draining`, `status`, `mode`, `active_provers`, `ring`, `size_bytes`, `data_shards`, `peer_materialized_frame`, `peer_head`, `peer_state`, `global_head`, `execution`, `local_execution_state`, `execution_detail`, `execution_severity`, `reward_units_per_frame`, `reward_quil_per_day`, `next_action`, and `default_action`. Available-shard rows omit worker/status/action fields but retain `peer_state`. `global_head` is either `null` or an object with `frame`, `global_frame`, and `generation`. `execution` is either `null` or an object with `state`, `blocker`, `materialized_frame`, `last_advance_unix_ms`, and `observed_unix_ms`.

`execution_detail` retains the Quilscan compatibility sentence, including the exact last-advance age, blocker/reason, and zero-materialized-frame warning. The latest official TUI footer uses age buckets and additional cadence/recovery/seal summaries, so its text is no longer byte-identical to this compatibility sentence. `execution_severity` is `normal` or `warning` and is the stable styling signal for non-TUI consumers. Both fields are emitted for every allocation; missing worker observations produce `Local execution details unavailable` with `normal` severity.

The official model controls status, default sorting, reward eligibility, and action hints. `size_bytes` and `reward_units_per_frame` are decimal strings to avoid precision loss in JavaScript. Reward forecasts use **8,000,000,000 base units per QUIL**, matching the official .106 correction; `reward_quil_per_day` is the official theoretical daily display string at **10 seconds/frame**, now retaining tenths (for example `"3.4"` or `"<0.1"`). `reward_quil_per_day_basis` explicitly identifies `"theoretical_10s_per_frame"`. Forecasts and token balances use the same base-unit conversion; the raw unit fields remain unchanged. Unknown ring/reward and missing shard observations are `null`; a known empty shard has `size_bytes: "0"`. A zero peer head becomes `null`. `peer_state` uses the official peer-materialization calculation. `local_execution_state` preserves full semantic names (`starting`, `waiting`, `syncing`, `serving`, `running`, `closing`, `handoff`, `blocked`, `stopped`, `stale`, `cached`, `unknown`), using the official model receipt/cache freshness. It never uses compact TUI labels such as `serve` or `close`. An older node reporting `blocked` / `awaiting successor` is classified as expected `handoff`; it does not produce warning severity. Zero local height warns only for fresh `running`/`serving`, matching official presentation. If `worker_info_available` is false, a `null` worker does not prove the allocation is unstaffed. An idle worker has an empty filter and `status: "idle"`. `worker_draining` is the actual flag for the matching core ID, including idle workers; it is null for unavailable/unmatched/unassigned workers and preserves explicit false. Counts and flags deduplicate repeated core IDs using the last record, matching the TUI. Draining is a lifecycle state, not proof of offline status. Independent RPC count observations need not agree exactly.

Additive schema-1 telemetry:

- Top-level `frame_cadence` contains the node-owned GLOBAL cadence; `allocation_scoring_strategy` is `null` when absent or empty.
- Allocation and available rows expose nullable `frame_cadence` and `prover_counts`; allocation rows also expose nullable `allocation_reason`.
- `execution.recovery` and `execution.seal` retain all corresponding official protobuf fields, including source timestamps, progress/attempt counts and seal submission/recording status. Recovery adds `failures_by_class` (an object from failure-class strings to uint32 counts) and `longest_permit_wait_ms` (a uint64 JSON integer, preserved through `u64::MAX`). Consumers requiring exact uint64 values must use an integer-capable JSON decoder; JavaScript Number cannot represent the full range. They are `null` on older nodes or before observations exist. Original `execution` fields keep their types and meanings.
- `frame_cadence` contains `last_observed_unix_seconds`, nullable `hour`/`day` windows, and raw `window_seconds`, `observed_seconds`, `advanced_frames`. These are observations, not client-inferred timing.
- `observed_reward_windows` contains `"60m"` and `"24h"`, each either `null` or `{ "units_per_day": "432000000000", "quil_per_day": "~54.0" }`. Exact units are decimal strings at 8,000,000,000 units/QUIL. The estimate is `per_frame × advanced_frames × 86400 / observed_seconds`, with integer division. Values are unavailable when cadence is missing, older than 90 seconds, future-dated, observed for less than 60 seconds or longer than its stated window. A fresh measured zero remains `"0"` / `"~0.0"`; it is distinct from `null`. Unknown shard rewards remain `null` even when cadence exists. Daily units are formatted directly and are never multiplied by the theoretical 8,640 frames/day again.

Confirmed joins/leaves expose `activating`/`departing` until the epoch boundary. Workers bound to a filter omitted from the live registry remain `bound` rows with worker/execution telemetry; their unavailable shard/reward fields stay `null` and they do not enter live allocation reward totals. Existing action strings retain absolute `@f…` thresholds even though interactive presentation now defaults to relative thresholds.

Agent migration: parse stdout as JSON and switch on `schema_version`. Do not parse TUI column spacing. Retain decimal strings until the display layer and ignore unknown additive fields. Existing schema-1 consumers remain compatible; legacy text-table consumers require migration.

## Authoritative Manage presentation (`tui`)

Schema 1 adds a structured `tui` presentation beside the unchanged machine fields. It calls the same view functions that print the interactive TUI headers, panel KPIs, cells, row details and styles. It never scrapes a terminal frame. Agent and web consumers should display this presentation and retain raw `filter`, `worker` and `status` identities for actions.

The top-level `tui` object contains `schema_version: 1` and `compact` / `expanded` objects. Each mode contains `header` (an array of KPI strings), `allocations` and `available_shards`. Each panel contains `heading` (an array of title/KPI strings) and `columns` (an ordered array of `{key, label}` string objects). Each raw row gains its own `tui.compact` and `tui.expanded`, with `cells` (strings keyed by column key), `detail` (the actual TUI footer text), `tone` (detail tone), and `tones` (cell tones keyed identically to `cells`). Presentation fields are never null. Tone names are `default`, `muted`, `success`, `warning`, `error` and `info`; other decorative colors normalize to `info`, while existing success/muted ring styles are retained.

Allocation column keys in display order are `filter`, `provers`, `prover_phases`, `ring`, `size`, `shards`, `local_mat`, `peer_head`, `global_head`, `interval`, `execution`, `reward`, `worker`, `status`, `mode`, `next_action`, `default_action`. Available keys are `filter`, `provers`, `prover_phases`, `ring`, `size`, `shards`, `peer_mat`, `peer_head`, `global_head`, `interval`, `peer_state`, `reward`. All nonselection columns are exported, including the normally optional phase breakdown. Filter cells retain the entire filter; spacing, cursor, clipping and terminal width are excluded. Compact and expanded modes use the actual TUI compact-action and compact-unit settings. Both observed windows and the theoretical reward window are included. Units and window order belong to the exported column labels.

This is the presentation of a fresh one-shot model. It applies worker/node observations before the shard refresh and runs the official progress-warning calculation before projecting either layout. Committed-head lag and per-row stalls derived from the current observations therefore follow the official TUI. Node-owned cadence/recovery/seal telemetry remains available, but a one-shot invocation cannot infer historical session stalls or retry history. The independently loaded verified Claimable reward KPI is omitted: Agent fetches and displays that witness separately. Other synchronously available KPIs come directly from the TUI helpers. Sorting arrows in labels describe the producer's row order. Consumers that apply their own sort should adjust their sort indicator separately.

## Official Token outputs

`token balance` no longer prints `Total balance: <decimal> QUIL`. For the QUIL application it prints independent claimable-reward, unshielded-legacy and confidential-coin lines, for example:

```text
Claimable prover rewards: <amount> QUIL (witness cites global frame <frame>; requires minting)
Unshielded legacy coins: <amount> base units across <count> coins (<shielded> already shielded)
Confidential coins: <amount> base units across <count> coins reported unspent by the configured node (not a finalized balance)
```

Each read has its own availability state. The claimable line can instead be `unavailable (...)`; that is not a verified zero. A missing confidential-coin root has an explicit rootless message and does not hide legacy/reward results. Any failed component still makes the command exit nonzero, so a parser must reject incomplete output. Token wallet base units use **8,000,000,000 units per QUIL**. Do exact integer/decimal conversion, not floating-point conversion. `--read-rpc` selects a node for wallet reads; reward witnesses still come from the configured submission node.

`token coins` prints a count of recovered unspent coins followed by `0x<address> <amount-in-base-units>` rows. `token confidential-address` prints the QCT3 receiving address and an escrow address on separate lines. `token legacy` reports legacy coins and an unshielded total in base units. Reward `token mint` is now two-stage: an authorization command saves bytes, then `token mint --claim <file>` submits the claim after finalization.

The official Token command set also includes `escrows`, `shield`, `shield-all`, `custom-mint`, `entitlements`, `payment-address`, `pay`, `prefund`, `prefunded`, and `settlement-claim`. Token commands accept `--application`, `--read-rpc`, `--max-pages`, and `--max-coins`. The shared wallet scan default follows official `.111` (`--max-pages 2048`, previously 128). Scans request up to 64 confidential coins or escrows per page; older nodes still answer pages of eight. The shared response-size bound scales with page size, up to 2 MiB for 64 entries. The local status extension below isolates that scan from the other two reads. Write operations add fee options and dynamic fee messages.

Consumers of the old `Total balance` line must migrate to the native-unit output. The streaming local interface below avoids coupling successful monitoring values to another section's failed scan.

`qclient token claimable-rewards` now streams three independent QUIL results: authenticated GLOBAL rewards, unshielded legacy coins and confidential balance. It calls the same official reward/listing/wallet scan/formatting functions as native balance. The reward query uses the submission node; legacy and confidential reads use the official read-node selection. All start concurrently. Reward and legacy reads have 30-second budgets; confidential discovery has no added overall deadline and retains the official per-RPC timeouts and page/coin limits. Each result is sanitized to one line, printed and flushed immediately in completion order. Already-shielded legacy coins are excluded from the legacy total; confidential coins remain node-reported unspent observations, not a finalized balance.

Each result can independently be `unavailable`; absent legacy identity, empty/all-shielded listings and a confirmed missing coin root retain the official distinct `none` descriptions. An unavailable witness, failed listing or absent result must never become a measured zero. The local command keeps its per-result read-failure/exit-zero convention; initialization and output errors can still fail the process. Native `token balance` retains its original output/exit rules.

Agent production now runs this one streaming command without an added process deadline. Agent shutdown still cancels it, explicit positive runner timeouts remain available to callers, and polling stays serial while a scan runs. Each valid line immediately updates only its section, even if another section fails, the process exits nonzero or the caller cancels it. Malformed/duplicate/oversized lines affect only their own section; missing sections are unsupported on a clean older build or errors on a failed process. Decimal strings remain exact. Values map to `qclient_claimable_rewards` (plus its witness frame), `qclient_legacy_balance` and `qclient_token_balance` (confidential). Each prefix carries `_read_state`, `_error`, `_attempted_at` and last-success `_refreshed_at`. Failed reads keep their own previous successful value/time. The frontend hides timeout errors and inline cache/offline notices at the user's request; other per-section errors remain visible. Known `none` is reported as zero with state `none`.

Process errors are separate and do not invalidate successful section updates. Token source revisions ignore routine metadata saves but reject stale in-flight results after wallet/node/process changes, removals and moves, including A→B→A. The user subsequently requested removal of automatic balance clearing: ordinary status publication and new source binding retain previously successful amounts, which change only when their own new query succeeds. Explicit node/qclient removal still resets the related status. Approximate service-start observations within the existing three-second tolerance are anchored to the last accepted start time, preventing macOS uptime rounding from invalidating valid reads on every poll. The frontend displays all three values in the existing compact Manage row; inline Cached/Offline/Last success text is hidden at the user's request, while per-query errors and timestamp tooltips remain. The existing reward list card keeps its eight-decimal display and exposes the exact value in its tooltip. New automatic fees and remote plaintext read-RPC restrictions remain official behavior.

## Official Prover read outputs

`node prover status` retains the basic `Peer ID`, `Version`, worker-count, `Last Received`, and `Reachable` lines consumed by the current Agent. Allocation hints use `Next Action:` and `Default Action:` with relative epoch-aligned frame thresholds. The JSON snapshot preserves absolute thresholds for compatibility. Worker rows add `Local execution:` with state, height, advance age, and observation age when available.

`node prover shards` shows observed 60m/24h cadence estimates beside a theoretical 10s/frame daily estimate; `shardinfo` retains its official reward presentation. Unknown ring/reward is `-`; the shards summary distinguishes known estimates from unknown ones.

`node prover manage --render` accepts `--width`, `--height`, `--keys`, `--color`, and `--timeout`; it drops mutating commands and reports them on stderr. `--help-text` renders controls without loading a node config or connecting. `--once` conflicts with both output modes and emits only JSON. All direct prover action arguments remain available.

An empty configured gRPC listener now selects local `127.0.0.1:8337`, unless official public/custom RPC selection applies. TLS endpoints install the required cryptographic provider and retain native-root certificate verification. Log commands honor configured master/worker log paths; cleaning preserves live logs and export applies the official redaction policy. These operations are covered by temporary-file fixtures, not executed on the operator’s real node during source verification.

## Official command synchronization and deferred adaptation

The complete 33-directory client dependency closure and protobufs follow official source `2db8107daed24650d563a0cd353e31301a52e622`. The previous .96 import introduced `node archive shards`, `node diagnostics health/resolve/request/status/fetch/pending/approve/deny`, and independent `diagnostics keygen` identities. Remote diagnostics/log sharing follows the latest official allowlist, signature, automatic/manual approval, sealing and expiry rules. With file logging, an enabled Node automatically approves log requests from allowed peers; journal-only Nodes retain operator approval. Existing machine operations report actual states and reject stale or already-approved preview attempts. Linux node log discovery uses official service-log resolution. The global signature flag accepts an explicit boolean, including `--signature-check=false`.

Client-generated Confirm messages retain `release: None` and legacy signed/canonical bytes; the client does not attest the node's release. The new official protocol release field is synchronized throughout the client dependency closure. Existing schema-1 identities, machine values, TUI presentation, once deadlines, independent claimable-reward output and release-manifest version authority remain unchanged. Existing Agent DTOs may ignore the two newly added recovery fields; they must retain every previously supported raw and TUI field.

## .106 scope boundary

This source sync includes all original .106 commands and shared-library behavior. The initial Worker/log follow-up preserves all existing schema-1 fields and adds nullable worker capacity/draining plus required incoming-log approval mode. The subsequent status-JSON integration below adds Gossip and complete per-Core execution observations through a separate read interface. Requester budget fields remain outside these follow-ups. The original interactive TUI and ordinary CLI follow official behavior, including corrected reward values.

The machine preview/export adapter uses the official shared log exporter, bundle sealing, selected configuration sources and home-path redaction. It does not override Node automatic log authorization or restore retired exporter/redaction implementations. Existing per-preview frozen ciphertext and token-map safeguards remain required.

## Incoming-log automatic approval mode

`node diagnostics machine --config-dir ABS_PATH list` now includes required `automatic: bool`, directly from the Node RPC. Schema version remains 1; requests, bundle limits, previews and terminal action DTOs keep their existing fields/types. Matching Agent decoding is required: old strict consumers reject the added field, and new strict consumers reject a missing/null/wrong-type mode rather than assuming manual approval.

Automatic mode refuses both Prepare and Approve after identity/status/expiry validation and before export/upload. Existing approval capability claim-before-config/RPC behavior remains unchanged. Deny/Withdraw/Discard continue to work. Agent rechecks the same Node's mode and pending request before manual actions, uses one shared five-minute action budget, and invalidates/cleans trusted native previews on automatic or changed/missing-request observations. Approval TTL may renew independently of pending and preparation expiry; reported receipt time may lead the Agent clock.

Settings displays actual runtime mode separately from saved configuration. File-log Nodes approve and export for allowlisted peers automatically; journal-only Nodes retain manual approval. Automatic or unavailable mode disables manual preview/approval, while denial/withdrawal remain available for actionable requests. Equal/unknown timestamps and stale callbacks cannot restore unsafe manual controls; a fresh View is required after an uncertain mode observation.

The incoming owner list does not contain requester remaining quota, next-request time or remote status denial details. These are not inferred from configuration or list size. No outgoing request UI, new autoApprove switch, Gossip fields or additional polling RPC is introduced.

## Status JSON for Gossip and Worker Execution

`qclient node prover status --json` is a local, read-only machine interface with `schema_version: 1`. The ordinary command without `--json` retains the official text output. This interface reads `GetNodeInfo` and `GetWorkerInfo` once each and does not query the shard table.

The top-level object contains node identity/basic status, `gossip_traffic`, `workers`, and nullable `worker_error`. All uint64 counters and timestamps are decimal strings, including frame heights, storage bytes, traffic counters and execution timestamps. Seniority is an arbitrary-size unsigned decimal string. Worker counts, Core IDs and other protobuf uint32 values remain JSON numbers. `worker_capacity` is null when zero/unreported. Optional execution heights and own-vote counts preserve null; an observed zero remains a decimal `"0"`.

`gossip_traffic.master` is the master's reported process traffic or null. `gossip_traffic.workers` contains only independently reported worker swarms, each with `core_id` and `traffic`; it is null when the Worker RPC fails, and an empty array when that RPC succeeds but no worker reports an independent swarm. Each process contains `uptime_ms` and the original class counters. Average Mbit/s is calculated separately against each process's uptime before summing. Message byte counts exclude gossip control messages and transport overhead. Shared-swarm workers are already included in master traffic; absence of an independent report does not imply an offline worker.

`workers` preserves the complete WorkerInfo list, including idle/unassigned and draining workers. Each row has Core ID, filter, available/total storage, management mode, draining, nullable execution and an `execution_detail` produced by the existing official formatter. Execution retains all raw observations and complete Recovery/Seal fields, including failure classes, longest permit wait, awaited frame, vote observations and source timestamps. Its nested gossip data is reported only in the top-level Gossip group to avoid duplication.

A failed NodeInfo read fails the command. A failed WorkerInfo read still returns valid node/master data with null worker arrays and a bounded UTF-8 error. Consumers retain previous successful Worker samples and mark them stale; they must not turn unavailable values into measured zeros.

Agent prefers this JSON and falls back to the old text command only when the installed qclient rejects `--json`. Gossip and Workers share the existing default 60-second status sampling during node verification; the browser's 5-second cache reads do not initiate Node RPCs. A no-argument `refresh_qclient_status` action permits an explicit refresh through the same serialized reader. These new tabs do not join Manage's 30-second refresh loop. This interface is independent of the compact-only Manage reports: Agent continues omitting all `tui.expanded` presentation.
